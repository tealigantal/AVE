# Knowledge System

## Purpose

AVE's Knowledge System preserves reusable knowledge without turning retrieval
into hidden authority. It separates knowledge claims from the project artifacts
and approvals that use them.

## Knowledge classes

| Class | Example | Required governance |
| --- | --- | --- |
| Editing knowledge | continuity, pacing, audio intelligibility | source/provenance, scope, version, evaluation |
| Creative pattern | contrast introduction, delayed reveal | applicability, evidence requirements, failure cases |
| User feedback | “keep pauses in interviews” | consent, creator/project scope, exact decision refs |
| Historical experience | a Skill worked for a specific project and outcome | immutable context snapshot, result, reviewer, limitations |
| Research knowledge | licensed style analysis or trend observation | checked date, rights, source snapshot, expiry |

## Storage and authority

Knowledge records are immutable by version and content identity. Project Host
assembles a bounded retrieval context and validates source, trust, license,
privacy, freshness, and compatibility before use. Model context is ephemeral;
it is not the system of record.

Project knowledge, user memory, and shared Skill knowledge are separate scopes.
A future shared catalog, cloud sync, or new database/process requires explicit
architecture, privacy, and security approval.

## Retrieval rules

Retrieval returns citations, applicability, conflicts, and uncertainty. Current
explicit intent and project evidence outrank generalized knowledge. A missing
or conflicting record degrades to explanation or alternatives, never to a
fabricated fact or silent fallback.

## Lifecycle

Knowledge may be proposed, reviewed, accepted for a scope, superseded, revoked,
expired, or deleted from future retrieval. Prior project decisions retain their
pinned provenance so they remain auditable after a knowledge version changes.
